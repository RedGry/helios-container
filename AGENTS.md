# Project Rules

Перед началом работы обязательно прочитай [CONTRIBUTING.md](CONTRIBUTING.md) и следуй описанному там процессу разработки, проверок, PR и релизов. При продолжении работы в новом чате читай актуальную версию файла, а не полагайся на прежний контекст.

## Branches and Pull Requests

- Основная стабильная ветка — `main`; все PR направляются в `main`.
- Новые возможности: `feature/<имя>`.
- Исправления: `bugfix/<имя>`.
- Подготовка выпуска: `release/<версия>`, например `release/0.1.0`.
- Не создавай ветки с префиксом `codex/` и не вводи `develop`: в проекте используется схема выше.
- Проверяй существующие ветки и переиспользуй подходящую. Не включай чужие незакоммиченные изменения в свои коммиты.
- Изменения готовь в соответствующей рабочей ветке и переноси в `main` через PR после проверок. Не делай commit/push напрямую в `main` и не сливай PR без явного поручения пользователя.

## Releases and Reviews

Проект работает на Rust; Python и Node.js используются для тестов и сборочных инструментов. Используй актуальный `tools/release.py` и проектный скилл `$helios-release`.

Заголовки секций PR и changelog можно писать на английском; описания изменений — на русском. Перед слиянием проверяй `scripts` и `release-check` для актуального коммита.

Обычный push не выпускает релиз. Создание тега, черновика и публикацию выполняй только в рамках явно порученного этапа.

## Release Tags

- Ветка `release/X.Y.Z` нужна для подготовки версии и changelog; постоянная отметка выпуска — тег `vX.Y.Z` на конкретном проверенном коммите `main`.
- Если изменения уже слиты в `main`, не откатывай их и не переноси повторно через релизную ветку. Проверь готовность выбранного коммита; отдельная ветка потребуется только для оставшихся изменений подготовки.
- Перед выпуском согласуй `VERSION`, `native/Cargo.toml` и раздел версии в `CHANGELOG.md`. Проверь CI выбранного коммита и отсутствие такого тега или релиза на GitHub, включая черновики.
- Не создавай и не отправляй тег заранее вручную: используй существующий ручной workflow `Release` на `main`, который привязывает выпуск к своему `$GITHUB_SHA`. Проверь этот SHA перед публикацией.
- Опубликованный тег и вложения выпуска не перемещай, не пересоздавай и не заменяй. Исправления выпускай под новым номером, например `v0.1.1` после `v0.1.0`.
- Черновик и публикация — отдельные этапы. Для уведомлений об обновлении нужен опубликованный стабильный GitHub Release; одного Git-тега недостаточно.

## Code Quality

Следуй `docs/code-quality.md`. Перед PR проверяй Rust через rustfmt, Clippy с `-D warnings` и тесты; PHP через `composer check` и HTTP-тесты шлюза. Не подавляй замечания линтеров вместо исправления причины. Проверки качества обязательны для веток и релиза.

Комментарии в новом коде не пишем. Используй понятные имена, явные типы и тесты поведения; пояснения процесса размещай в Markdown.
