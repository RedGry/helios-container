# Helios Release

Используй существующий `tools/release.py` и ручной workflow `Release`. Не создавай второй сборщик. Подготовка версии не разрешает создание тега, черновика или публикацию. Следуй явно запрошенному этапу.

Проверь корень Git и remote. Родительский каталог содержит частные SSH-помощники и не является источником релиза. Прочитай `CONTRIBUTING.md`, `CHANGELOG.md`, `VERSION`, `native/Cargo.toml`, `native/src/update.rs`, `tools/release.py` и `.github/workflows/release.yml`.

`main` — стабильная и целевая ветка PR. Используй `feature/<имя>`, `bugfix/<имя>` и `release/X.Y.Z`; `develop` не используется. Следуй `AGENTS.md`. Не используй `codex/`, не переноси чужие незакоммиченные изменения.

## Подготовка

Для оставшихся изменений версии и changelog используй `release/X.Y.Z` и PR в `main`. Если нужные изменения уже в `main`, не откатывай и не переноси их заново: используй проверенный коммит. Сам запрос подготовки релиза не разрешает прямой push в `main` или слияние PR.

1. Проверь состояние Git, последний опубликованный релиз и теги. Используй заданный номер `X.Y.Z`, согласуй `VERSION` и Cargo. `0.0.0` выпускать нельзя.
2. Перенеси готовые изменения из `Unreleased` в раздел `## X.Y.Z`, сохрани историю. Заголовки секций `New Features`, `Bug Fixes`, `Documentation`, `Changelog`, текст на русском. Не выдумывай PR и результаты проверок.
   Для первого релиза опиши весь доступный функционал выбранного коммита `main` по README, руководствам и реализации, а не только последние изменения. Включай только слитые возможности; проверь актуальный `main` перед сборкой. Не описывай внутренние исправления до первого выпуска как регрессии опубликованной версии.
3. На FreeBSD 14 amd64 выполни команды из `CONTRIBUTING.md`, затем `python3 tools/release.py --check`, `python3 tools/release.py --binary native/target/release/helios-container-native` и `python3 tools/release.py --verify`.
4. Комплект в `dist/` содержит ровно `helios-container-freebsd-amd64`, `helios-container-freebsd-amd64.sha256`, `VERSION`, `release-notes.md`. Updater ожидает первые три файла, SHA-256 в GNU-формате. Проверь FreeBSD ELF64 amd64 и `--build-version`. Не включай VM, QEMU, конфигурации, ключи, ссылки и временные файлы. Python нужен только для разработки, в установленном kit его нет.
5. Проверь `scripts`, `release-check` и артефакт `release-preview` текущего коммита. Unit-тесты не заменяют установку и обновление на FreeBSD. Не останавливай рабочую VM ради проверки без разрешения.

## Черновик и публикация

Только по поручению создания релиза проверь версию и changelog в нужном коммите `main`, отсутствие такого тега и черновика. При неизвестном результате сначала прочитай состояние, не создавай дубль.

Теги стабильных выпусков имеют вид `vX.Y.Z`; `release/X.Y.Z` — рабочая ветка подготовки. Не создавай и не пуши тег вручную заранее. Workflow привязывает выпуск к своему `$GITHUB_SHA`; проверь, что это проверенный коммит `main` с нужной версией. Опубликованные теги не перемещай, не удаляй для повторного выпуска и не пересоздавай. Для исправления опубликованной версии увеличь номер.

Запусти ручной workflow `Release` на `main`, дождись проверок и проверь commit, описание и три вложения черновика. Push сам по себе не создаёт релиз. Запрос «подготовь релиз» разрешает подготовку; «создай черновик» — черновик; явный запрос «выпусти / сделай релиз X.Y.Z» разрешает весь процесс, включая слияние PR подготовки после обязательных проверок и публикацию стабильного выпуска. Не запрашивай повторное разрешение на уже порученный этап. После проверки черновика опубликуй его как стабильный Latest только в рамках такого запроса. Не заменяй вложения уже опубликованной версии.
