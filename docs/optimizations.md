# Ускорение сборки и запуска приложений

В Helios Container CPU Linux VM эмулируется через QEMU TCG. Компиляция, JIT и загрузка больших Java-приложений могут занимать минуты. Настройки помогают сократить лишнюю работу, но результат зависит от приложения и нагрузки общего хоста.

Команды ниже выполняются на helios, кроме явно отмеченных примеров. `/workspace/my-app` — пример каталога проекта **внутри Linux VM**, `app` — пример имени сервиса Compose. Замените их своими значениями. Работа с файлами описана в [руководстве](guide.md).

## Сначала определите, что занимает время

Измеряйте отдельно сборку исходников, передачу файлов, сборку образа и время от запуска контейнера до готовности API. Статус `running` означает, что процесс запущен; приложение ещё может загружаться.

```sh
docker compose -f /workspace/my-app/compose.yaml ps
docker compose -f /workspace/my-app/compose.yaml logs --tail 100 app
docker stats --no-stream
helios-container status
```

Признаки разных проблем:

| Что видно | Что проверять |
| --- | --- |
| Долго выполняется Maven, Gradle или npm | Возможность собирать вне эмуляции, кеш зависимостей |
| Долго передаётся build context | `.dockerignore`, размер исходников и артефактов |
| При каждом обновлении скачивается одна и та же база | Порядок слоёв Dockerfile, использование кеша |
| Процесс работает, но API ещё недоступен | Загрузку приложения, миграции, доступность БД, healthcheck |
| Контейнер падает или deployment откатывается | Ошибки, OOM и внутренние таймауты приложения |
| API готов внутри VM, а снаружи 502/504 | Адрес upstream, nginx, проброс портов и таймауты шлюза |

## Собирайте исходники вне эмулируемой VM

Для Java можно собрать JAR/WAR на компьютере разработчика, в CI или непосредственно на helios, если там доступен совместимый JDK. Frontend также удобнее собирать на компьютере разработчика. В VM передавайте готовые артефакты и конфигурацию контейнера.

Пример на машине с исходниками и Maven:

```sh
./mvnw package
```

Сохраняйте проверки проекта при обычной сборке. Если артефакт включает нативные библиотеки, они должны соответствовать Linux и архитектуре контейнера: сборка на другой ОС требует отдельной проверки совместимости.

Runtime Dockerfile для исполняемого Spring Boot JAR может выглядеть так:

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/app.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

Замените имя JAR и версию Java на используемые в проекте. Базовый образ для воспроизводимых сравнений фиксируйте по digest. Этот пример подходит для исполняемого JAR; WAR для WildFly требует образа сервера приложений.

## Уменьшите контекст и сохраняйте кеш Docker

Для предыдущего Dockerfile достаточно такого `.dockerignore`:

```dockerignore
**
!Dockerfile
!target/
!target/app.jar
```

Если Dockerfile копирует другие файлы, добавьте их в список разрешённых. Пароли, `.env`, приватные ключи и рабочие каталоги не должны попадать в образ. Не используйте `--no-cache` и очистку образов перед каждым обновлением: это заставляет повторять работу.

При сборке внутри Docker размещайте редко меняющиеся зависимости раньше исходников. Для нескольких Java-сервисов используйте общую базу с JRE/WildFly и отдельный образ для каждого JAR/WAR. Тогда изменение одного приложения не меняет образ другого.

Обновление только одного сервиса:

```sh
docker compose -f /workspace/my-app/compose.yaml build app
docker compose -f /workspace/my-app/compose.yaml up -d --no-deps --wait --wait-timeout 900 app
```

`--no-deps` подходит, когда зависимости уже запущены и их конфигурация не менялась. Сервис должен иметь healthcheck, иначе ожидание Compose не доказывает готовность API. После обновления отдельно проверьте опубликованный URL.

## Подберите ресурсы VM по замерам

```sh
helios-container stop
helios-container configure --memory 4096 --cpus 2
helios-container start
```

Остановка VM прерывает работу всех её контейнеров. CLI поддерживает 512–16384 МиБ памяти и 1–8 vCPU; действуют также ограничения аккаунта. Сравнивайте ресурсы на своей нагрузке: больше vCPU под TCG не гарантирует более быстрый запуск и не резервирует физические ядра хоста.

Оставляйте память для Linux, Docker, БД и других сервисов. JVM heap занимает только часть памяти Java-процесса: нужны также metaspace, стеки и нативные буферы. Увеличение RAM полезно при нехватке памяти; само по себе оно не устраняет стоимость эмуляции CPU.

### Профиль 8 vCPU

Для параллельного старта тяжёлых приложений можно явно выбрать 8 vCPU и 4096 МиБ RAM:

```sh
helios-container stop
helios-container configure --memory 4096 --cpus 8
helios-container start
```

Значения по умолчанию остаются 1 vCPU и 1024 МиБ. Профиль 8 vCPU не включается автоматически: общий хост обслуживает несколько пользователей, а число vCPU не гарантирует выделенную долю CPU. QEMU запускается со стандартным приоритетом; приоритет выше стандартного не является способом справедливо распределить ресурсы между аккаунтами. Для гарантированного ограничения расхода CPU нужны квоты хоста.

В одиночных замерах soa-lab2 6–7 октября 2026 на FreeBSD с QEMU 11.1.1 TCG измерялось время от готовности Docker после перезапуска VM до `healthy` у Catalog, Agency и PostgreSQL. Память оставалась 4096 МиБ, образы и параметры JVM не менялись:

| vCPU | Время до готовности сервисов |
| --- | ---: |
| 4 | 390,9 с (6:31) |
| 8 | 290,9 с (4:51) |
| 12, экспериментальный прямой запуск QEMU | 289,7 с (4:50) |
| 16, экспериментальный прямой запуск QEMU | Полного результата нет: потеряна SSH-связь |

В этом сравнении 8 vCPU дали примерно 26% сокращения времени относительно четырёх; дополнительного выигрыша от 12 не видно. Это одиночные запуски с дискретной проверкой healthcheck, а не доказательство устойчивого ускорения. Без повторных замеров и теста одновременной работы разных аккаунтов нельзя гарантировать тот же эффект или отсутствие влияния на соседних пользователей. Потеря связи во время проверки 16 vCPU не устанавливает причину недоступности сервера.

`healthy` ещё не гарантирует готовность всех межсервисных маршрутов: на 8 и 12 vCPU первый запрос Agency к Catalog получил HTTP 504. На 12 после прогрева прошли 24 запроса с шестью параллельными исполнителями без ошибок. Проверяйте опубликованный API отдельно; увеличение vCPU не устранило задержку первого запроса.

Сборки, в которых разрешено только 1–4 vCPU, необходимо обновить перед использованием этого профиля. Для возврата к четырём:

```sh
helios-container stop
helios-container configure --cpus 4
helios-container start
```

## Параметры Java для эксперимента

Для HotSpot Java 17 можно сравнить обычный запуск с `-XX:TieredStopAtLevel=1`: он ограничивает JIT уровнем C1, уменьшая работу компилятора на старте. Возможна потеря производительности после прогрева. Этот приём рассматривается в [материале Spring о времени запуска](https://spring.io/blog/2018/12/12/how-fast-is-spring/).

Пример фрагмента Compose для сервиса с исполняемым JAR:

```yaml
services:
  app:
    environment:
      JDK_JAVA_OPTIONS: "${APP_STARTUP_OPTS:--XX:TieredStopAtLevel=1}"
```

`APP_STARTUP_OPTS` здесь — переменная примера, которую вы добавляете в свой Compose. Если `JDK_JAVA_OPTIONS` уже используется, сохраните существующие параметры, включая память и TLS. Для WildFly проверьте стартовый скрипт: он может использовать `JAVA_OPTS`.

В `.env` рядом с Compose **в VM** можно попробовать:

```dotenv
APP_STARTUP_OPTS="-XX:TieredStopAtLevel=1 -XX:ActiveProcessorCount=2 -XX:+UseSerialGC"
```

`ActiveProcessorCount=2` меняет число CPU, видимых JVM, и влияет на размеры некоторых пулов; это не лимит CPU контейнера. `UseSerialGC` выбирает последовательный сборщик: на небольшой нагрузке он может уменьшить накладные расходы, но при большом heap способен увеличить паузы. Проверяйте и запуск, и запросы после прогрева. Описание параметров: [документация Java 17](https://docs.oracle.com/en/java/javase/17/docs/specs/man/java.html).

После изменения `.env` выполните `compose up`, как в примере выше. `docker restart` не применяет изменения конфигурации Compose. Переменные оболочки FreeBSD не следует считать автоматически переданными в Compose внутри VM; используйте файл `.env` в VM или явно задавайте окружение через `helios-container ssh`.

Для возврата к C1-профилю сохраните `APP_STARTUP_OPTS=-XX:TieredStopAtLevel=1` и повторите `compose up`. Для возврата к настройкам до эксперимента восстановите прежнее окружение Compose и `.env`; удаление только переменной оставит C1 из значения по умолчанию в этом примере.

## Готовность, порядок запуска и 502/504

Добавьте healthcheck, который проверяет реальную готовность API, включая необходимые зависимости. Команда проверки должна существовать в образе. Например, для образа с `curl` и доступным endpoint `/actuator/health`:

```yaml
services:
  app:
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/actuator/health"]
      interval: 30s
      timeout: 5s
      start_period: 10m
      retries: 3
```

Endpoint Actuator должен быть подключён и показывать нужную приложению готовность. `start_period` даёт время на загрузку до учёта неудачных проверок; он не заставляет ждать 10 минут после первого успеха. Если версии Docker/Compose поддерживают `start_interval`, можно задать `start_interval: 10s` для более частых проверок во время старта. См. [параметры Compose](https://docs.docker.com/reference/compose-file/services/#healthcheck).

Используйте `depends_on: condition: service_healthy` для обязательных зависимостей, например БД. Независимые приложения можно запускать параллельно. `service_started` безопасен только если потребитель умеет пережить ещё не готового соседа. Пример условий есть в [документации Docker](https://docs.docker.com/compose/how-tos/startup-order/). Условия запуска не обеспечивают автоматическую готовность после произвольного `docker restart`.

У WildFly долгий запуск может превысить внутренний таймаут и откатиться. В проверенном приложении помог параметр:

```text
-Djboss.as.management.blocking.timeout=1200
```

Он предотвращает преждевременный откат, но не ускоряет запуск. Длинный `--wait-timeout` Compose не заменяет внутренний таймаут WildFly. Подробности: [руководство WildFly 26](https://docs.wildfly.org/26/Admin_Guide.html).

Отключайте ненужные подсистемы сервера только после проверки приложения. Например, у Spring WAR без CDI удалось убрать лишнее сканирование Weld; для приложения с CDI/EJB такое изменение может сломать deployment.

Во время пересоздания единственного экземпляра сервиса API временно недоступен. Healthcheck и увеличение таймаутов не обеспечивают непрерывную доступность. Если ошибки остаются после успешной проверки API внутри VM, проверяйте nginx и опубликованный маршрут отдельно.

## Как сравнивать настройки

Сначала сохраните текущие Compose, `.env` и ресурсы VM для отката. Используйте одинаковые артефакты, образы и данные; меняйте одну группу параметров. Чередуйте исходный и экспериментальный профили, сделайте хотя бы несколько запусков каждого и записывайте нагрузку хоста. Для серьёзного вывода двух запусков недостаточно.

При уже работающих зависимостях и настроенном healthcheck можно измерить перезапуск одного сервиса:

```sh
time docker compose -f /workspace/my-app/compose.yaml up -d \
  --no-deps --no-build --force-recreate --wait --wait-timeout 900 app
```

Команда прерывает доступ к этому сервису. Она измеряет полный путь через CLI до готовности Compose, поэтому дополнительно сохраняйте время загрузки из логов приложения. Перезапуск контейнера на работающей VM и холодный запуск всей VM — разные эксперименты.

После каждого профиля проверьте опубликованный API, несколько параллельных запросов и операции записи на тестовых данных. Сравнивайте время ответов и ошибки после прогрева, а не только скорость загрузки.

### Пример: soa-lab2

Замеры Catalog 6 октября 2026: VM 4 vCPU / 4096 МиБ, Java 17, WildFly 26.1.3.Final, одинаковые образы и WAR. Пересоздавался только Catalog; Agency, PostgreSQL и nginx продолжали работать. VM не перезагружалась, кеши не сбрасывались.

| Профиль | Запуск 1 до готовности API | Запуск 2 | Среднее |
| --- | ---: | ---: | ---: |
| C1: `-XX:TieredStopAtLevel=1` | 304,518 с | 259,640 с | 282,079 с |
| C1 + `ActiveProcessorCount=2` + `UseSerialGC` | 280,881 с | 259,360 с | 270,121 с |

Разница средних — около 12 секунд (4,24%), но во второй паре всего 0,280 секунды. Эти данные **не доказывают устойчивого ускорения**: разброс между запусками больше наблюдаемого эффекта. Компактный профиль прошёл 24 запроса с 6 параллельными исполнителями без HTTP-ошибок и временный CRUD-тест на небольших данных. Это проверка корректности, а не доказательство эффективности при большой нагрузке.

## Ограничения настроек QEMU

Текущий kit запускает QEMU с `-accel tcg -cpu max`; CLI не предоставляет переключатель аппаратного ускорения или размера кеша трансляции. В проверенной VM не было данных, подтверждающих пользу увеличения этого кеша. Ручное увеличение кешей, количества потоков или памяти без замеров не даёт основания ожидать ускорения.

Начните с переноса сборки, уменьшения контекста, кеширования образов и обновления только нужного сервиса. Затем сравнивайте ресурсы и настройки конкретного приложения с сохранённым вариантом отката.
