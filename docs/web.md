# Веб-шлюз · опционально

Публикуйте HTTP backend через `https://se.ifmo.ru/~USERNAME/`, даже если он работает внутри Docker VM. Frontend остаётся в `~/public_html`, внешний порт и SSH-туннель не нужны.

## Включение

Сначала запустите приложение. Для контейнера опубликуйте его порт **в Linux VM**:

```sh
docker run -d --name web --restart unless-stopped -p 8080:80 nginx:alpine
helios-container web install
```

Команда создаёт `index.php` и `.htaccess` в `~/public_html/helios-container`. `.htaccess` разрешает HTTP-методы REST API только в каталоге шлюза. Ваши существующие страницы и корневой `index.html` сохраняются. Занятый каталог шлюза установщик не перезаписывает. Проверка исполнения PHP проходит до размещения рабочего шлюза.

Установщик выводит страницу и **приватную ссылку управления**. Ссылка доступна повторно через:

```sh
helios-container web info
```

Откройте приватную ссылку. Во вкладке «Порты» — форма с полем портов и кнопкой сохранения:

| Ввод | Backend | Публичный путь после `index.php` |
| --- | --- | --- |
| `8080` | Порт 8080 внутри вашей VM | `/vm/8080/` |
| `8080, 8081` | Два порта внутри вашей VM | `/vm/8080/`, `/vm/8081/` |
| `host:3000` | Порт вашего процесса на helios | `/host/3000/` |
| Пустое поле | Закрыть все опубликованные маршруты | — |

Форма заменяет весь список опубликованных маршрутов. Можно указать до 8 портов. Для VM нужен уже запущенный kit: `helios-container start`. Внутренний loopback-проброс QEMU на helios создаётся автоматически. Браузер и студент не настраивают SSH-туннель.

Для `host:3000` процесс должен принадлежать вашему пользователю и слушать IPv4 `127.0.0.1:3000` или `0.0.0.0:3000`. Предпочтительнее loopback. Проверка владельца выполняется при сохранении и при каждом запросе. Произвольные URL и порты чужих процессов шлюз не принимает.

## Личная панель

На этой же странице откройте вкладку «Контейнеры и логи». Она использует тот же приватный ключ и показывает:

- Запущена ли VM, сколько ей выделено vCPU и RAM.
- Все контейнеры вашей VM, включая остановленные, их образы, состояние и health status, если настроен healthcheck.
- CPU, память с лимитом, сетевой и дисковый I/O, число процессов. Значения Docker относятся к гостевой Linux VM. Расход QEMU на helios будет выше.
- Порты контейнеров и опубликованные HTTPS-адреса, в том числе маршруты к обычным процессам на helios. Проверка «TCP слушает» не гарантирует готовность приложения.
- Последние 100–1000 строк stdout/stderr выбранного контейнера, максимум 128 КиБ. Логи обновляются отдельной кнопкой. Файлы внутри контейнера и логи обычных процессов на helios эта панель не читает.

Панель только для просмотра. Остановленная VM не запускается автоматически. Polling состояния выполняется каждые 10 секунд, пока открыта вкладка панели и видима страница браузера. Его можно отключить. Агент кеширует снимок Docker на 5 секунд. При загрузке VM показывается сообщение о недоступности Docker.

Протокол приложения нельзя определить по номеру TCP-порта. Если хотите показывать его в панели, укажите labels при создании контейнера:

```sh
docker run -d --name web -p 8080:80 \
  --label helios-container.protocol=http \
  --label helios-container.polling=false nginx:alpine
```

В Compose те же значения задаются в `services.<имя>.labels`. Допустимые протоколы: `http`, `https`, `tcp`, `udp`. Для polling — `true` или `false`. Это декларация владельца приложения, не результат сетевого теста. Без labels отображается «не указан». Polling интерфейса панели и polling вашего приложения — разные вещи.

Внешние ссылки шлюза используют HTTPS, от PHP до агента и опубликованного backend идёт HTTP. Для HTTPS-only backend нужен свой HTTP reverse proxy, как nginx. HTTPS-контейнер сам по себе не получает поддержку в HTTP-шлюзе. WebSocket и SSE остаются недоступны через текущий хостинг.

Для обновления ранее установленного kit повторите команду установки, затем выполните `helios-container web stop` и `helios-container web install`. VM и контейнеры перезапускать не нужно. Приватный ключ и список портов сохраняются.

## Подключение frontend

Скопируйте адрес из формы и используйте его как base URL API:

```js
const API = '/~USERNAME/helios-container/index.php/vm/8080';
const response = await fetch(`${API}/api/health`);
const result = await response.json();
```

Если backend слушает `/api/health`, шлюз передаст ему именно этот путь. Query-параметры и тело запроса сохраняются. `Authorization` также передаётся приложению.

Для frontend на `se.ifmo.ru` запрос остаётся на том же origin — CORS не нужен. Если frontend работает, например, на `http://localhost:5173` или другом домене, настройте CORS в backend. Его заголовки шлюз передаёт. Сам шлюз не разрешает все внешние origins.

Редиректы на абсолютный путь вроде `/login` и cookie `Path=/` получают префикс шлюза. Cookies с атрибутом `Domain` становятся host-only. Backend получает `X-Forwarded-Proto: https`, `X-Forwarded-Host: se.ifmo.ru` и `X-Forwarded-Prefix`. При необходимости настройте в приложении поддержку reverse proxy и внешний base URL. HTML и JavaScript шлюз не переписывает — приложения с жёстко заданными абсолютными путями потребуют настройки.

## Как устроено

```text
Браузер → HTTPS se.ifmo.ru → PHP в public_html
        → HTTP-агент на 127.0.0.1 под вашим пользователем
        → ваш backend на helios / loopback-проброс QEMU → контейнер
```

На проверенном helios PHP выполняется от `www`, не от студента. Поэтому PHP не меняет приватные файлы kit, не запускает QEMU и не выполняет команды оболочки. Он передаёт запросы небольшому агенту на Python из стандартной библиотеки. Агент работает под студентом, хранит настройки с правами `600` и настраивает только его VM.

Публичная PHP-страница не содержит ключ управления. Ключ приходит во фрагменте приватной ссылки (`#key=…`), не отправляется в URL HTTP-запроса и убирается из адресной строки. Он используется в заголовке для настройки портов, просмотра состояния и логов. В cookies и localStorage не сохраняется. Логи могут содержать секреты приложения. Не публикуйте эту ссылку в frontend или репозитории.

Публичный API доступен всем, кому известен адрес. Защита формы **не защищает backend**: используйте авторизацию самого приложения. Не публикуйте Docker API, базу данных или административную HTTP-панель без её собственной защиты. Все пользовательские каталоги `~USERNAME` разделяют origin `se.ifmo.ru`. Разные пути не создают изоляцию доменов для JavaScript и cookies.

## Ограничения

- Только HTTP backend по IPv4. TCP-сервисы вроде PostgreSQL, UDP и WebSocket через этот шлюз не поддерживаются.
- Методы: GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS. Тело запроса до 8 МиБ, ответ до 16 МиБ. Лимиты PHP и веб-сервера могут быть строже.
- Ответ буферизуется. SSE, длительный streaming и chunked-загрузка не поддерживаются.
- `multipart/form-data` не поддерживается: PHP разбирает такое тело до выполнения скрипта. Для API используйте JSON или `application/octet-stream`.
- Таймаут backend — 15 секунд. PHP ждёт агент до 20 секунд. Это шлюз для обычного студенческого API, а не длительных сборок и задач.
- Одновременно агент обслуживает до 8 запросов. Его память и CPU расходуют лимиты владельца kit. PHP обслуживается общей инфраструктурой хостинга.
- Нужен PHP ≥ 8 с `allow_url_fopen`, поддержка `PATH_INFO`, доступ PHP к loopback helios, разрешение AuthConfig для `.htaccess` и утилита `sockstat`. PHP-cURL не требуется. На helios эти возможности проверены.
- Работающий backend и агент должны оставаться запущенными. Агент переживает выход из SSH. После перезапуска сервера вызов `docker`/`helios-container start` поднимет агент, если шлюз установлен. Отдельно можно выполнить `web start`.

## WebSocket

Через текущий хостинг `se.ifmo.ru/~USERNAME/` WebSocket не работает. Проверка на helios показала, что внешний nginx не передаёт `Upgrade` и `Connection`, а Apache не загрузил `mod_proxy`, `mod_proxy_http` и `mod_proxy_wstunnel`. Установка пакетов в HOME и `.htaccess` не меняют конфигурацию внешнего nginx и не включают серверные модули Apache.

Для стандартного WSS по этому адресу администраторы должны настроить прохождение WebSocket через nginx и reverse proxy Apache до вашего backend. Это также потребует отдельного маршрута, обходящего PHP-шлюз. [nginx: WebSocket proxying](https://nginx.org/en/docs/http/websocket.html), [Apache: WebSocket tunneling](https://httpd.apache.org/docs/2.4/mod/mod_proxy_wstunnel.html).

Без этих изменений можно использовать отдельный доступный WSS-шлюз на другом домене или HTTP polling, если приложение его поддерживает. Например, [Socket.IO поддерживает транспорт polling](https://socket.io/docs/v4/client-options/#transports), но это не замена произвольному WebSocket-серверу. Текущие таймауты и лимиты HTTP-шлюза сохраняются. Ответ на polling-запрос должен приходить быстрее 15 секунд.

## Управление и удаление

```sh
helios-container web info
helios-container web stop
helios-container web start
helios-container web remove
```

`stop` отключает агент. Страница сохранится, API вернёт ошибку недоступности. `remove` удаляет только PHP-страницу и `.htaccess` шлюза, его настройки, процесс и лог. Frontend, VM, контейнеры и ранее созданные loopback-пробросы сохраняются. Полное `helios-container uninstall --yes` также убирает установленный шлюз.

Лог запуска — `~/.local/helios-container/web.log`. Настройки и приватная ссылка — в `web.json` внутри того же приватного каталога. Не копируйте его в `public_html`.

Техническая основа: [HTTP streams PHP](https://www.php.net/manual/en/context.http.php), [Apache PATH_INFO](https://httpd.apache.org/docs/2.4/mod/core.html#acceptpathinfo).
